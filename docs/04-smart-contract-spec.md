# 04 — Smart contract spec

Rust, `near-sdk` 5.x (5.30.1, with the `unstable` feature, which is what exposes `env::ecrecover`), built with `cargo-near` 0.23. One contract instance serves many runs. Directory: `contracts/blindroll/`.

## Config (set in `new`)

| Field | Type | Meaning |
|---|---|---|
| `owner` | `AccountId` | Can update `relayer` and pause |
| `token_id` | `AccountId` | The USDC NEP-141 contract accepted for funding |
| `relayer` | `AccountId` | Informational; claims are authorized by signatures, so anyone may submit |
| `paused` | `bool` | Blocks `create_run`, funding and claims |

## Run

```rust
pub struct Run {
    pub run_key: String,              // backend UUID, <= 64 chars, unique
    pub creator: AccountId,
    pub approvers: Vec<AccountId>,    // 1..=10
    pub threshold: u8,                // 1..=approvers.len()
    pub approvals: Vec<AccountId>,
    pub merkle_root: [u8; 32],
    pub report_hash: [u8; 32],
    pub recipient_count: u32,
    pub total_amount: u128,           // USDC base units (6 decimals)
    pub funded_amount: u128,
    pub claimed_amount: u128,         // includes in-flight transfers
    pub reclaimed_amount: u128,       // sent to refund_account by reclaim_unclaimed (includes in-flight)
    pub claim_deadline_ms: u64,
    pub refund_account: AccountId,    // receives unclaimed funds after the deadline
    pub status: RunStatus,            // Draft | Approved | Active | Closed | Cancelled
}
```

Storage: `runs: LookupMap<String, Run>`, `claimed: LookupSet<[u8; 32]>` keyed by `sha256(run_key || leaf_hash)`. A third map, `runs_by_approver: LookupMap<AccountId, Vec<String>>`, backs the `get_runs_by_approver` view.

**Storage charge.** `create_run` requires an attached deposit of `run storage bytes × storage_byte_cost + recipient_count × (100 bytes × storage_byte_cost + 0.00125 NEAR)` and refunds the rest. The per-recipient part (0.00225 NEAR) prepays the `claimed` record and the token `storage_deposit` for that recipient's payout target, so claims do not drain the contract's own balance.

## Leaf and Merkle format (must match `packages/core` exactly)

```
leaf_preimage = "blindroll:leaf:v1|" + run_key + "|" + chain + "|" + address + "|" + amount + "|" + salt_hex
leaf_hash     = sha256(utf8(leaf_preimage))
```

- `chain` ∈ `near`, `evm`, `solana`.
- `address`: NEAR account ID as-is; EVM lowercase `0x` + 40 hex; Solana base58.
- `amount`: decimal string of USDC base units, no leading zeros (e.g. `1000000000` = 1,000 USDC).
- `salt_hex`: 32 lowercase hex chars (16 random bytes).
- The `leaf` argument of the claim methods is JSON `{ "chain", "address", "amount", "salt_hex" }` (`amount` is a string). `run_key` always comes from the method argument, never from the leaf.
- **Internal node** = `sha256(min(a, b) || max(a, b))` (sorted pair, byte-wise comparison). No index needed in proofs.
- Odd node at a level is promoted unchanged.
- Single-leaf tree: root = leaf hash, proof = `[]`.
- Proofs are arrays of 64-char lowercase hex strings, at most 32 items.

### Input validation (identical in `packages/core` and the contract)

The leaf preimage uses `|` as a delimiter and the claim message uses `\n`, so no field may contain `|`, `\n` or `\r`. Both implementations enforce this by accepting only these alphabets, and reject everything else:

| Field | Rule |
|---|---|
| `run_key` | `[A-Za-z0-9_-]{1,64}` |
| `chain` | exactly `near`, `evm` or `solana` |
| `address` (near) | a valid NEAR account ID (2–64 chars, lowercase) |
| `address` (evm) | `0x` + 40 lowercase hex (checksummed/mixed-case addresses are rejected; lowercase first) |
| `address` (solana) | 32–44 base58 chars |
| `amount` | canonical decimal: `[1-9][0-9]*`, fits in `u128` (no zero, sign, leading zeros or decimals) |
| `salt_hex` | 32 lowercase hex chars |
| hashes, proof items | 64 lowercase hex chars |
| `destination_asset`, `destination_address` (claim message) | 1–128 printable ASCII chars (0x20–0x7e) except `|` |
| `payout_target`, `contract_id` (claim message) | valid NEAR account IDs |

Rejections are covered by the `invalid_leaves`, `invalid_proofs` and `invalid_messages` lists in the shared vectors, tested in both languages.

Shared test vectors live in `packages/core/test-vectors/merkle.json` and `claim-message.json`. They are generated by `pnpm vectors` (`packages/core/scripts/gen-vectors.ts`) and tested in both TypeScript (`vitest`, which also fails if the committed files drift from the generator) and Rust (`cargo test`, unit and sandbox).

### Run lifecycle
| Method | Caller | Behaviour |
|---|---|---|
| `create_run(run_key, approvers, threshold, merkle_root_hex, report_hash_hex, recipient_count, total_amount: U128, claim_deadline_ms, refund_account)` | anyone (`#[payable]` for storage) | Validates inputs, `run_key` unique, deadline in the future, `total_amount > 0`. Status `Draft`. Emits `run_created` |
| `approve_run(run_key)` | an approver | Only while the run is `Draft`. Adds approval once; if approvals ≥ threshold → `Approved`. Emits `run_approved` |
| `cancel_run(run_key)` | an approver | Only if `funded_amount == 0` and status is `Draft` or `Approved` → `Cancelled`. Emits `run_cancelled` |
| `ft_on_transfer(sender_id, amount, msg)` | the USDC contract | `predecessor == token_id`; `msg` = `{"fund_run":"<run_key>"}`; run must be `Approved` (funding may arrive in several transfers); accept up to `total - funded`, return the rest as unused; when `funded == total` → `Active`. Any other status, a bad `msg`, an unknown run, a paused contract or a passed deadline → return the full amount. A call from any other token panics. Emits `run_funded`. The Blindroll contract must be registered on the token (`storage_deposit`) before the first `ft_transfer_call` |
| `reclaim_unclaimed(run_key)` | anyone | After `claim_deadline_ms`, for an `Approved` (partly funded), `Active` or `Closed` run; transfers `funded - claimed - reclaimed` to `refund_account` (same `storage_deposit` + `ft_transfer` receipt as claims); status `Closed`; `reclaimed_amount` increases. Emits `run_closed`. If the transfer fails, the callback `on_reclaim` restores `reclaimed_amount` (emits `reclaim_failed`) and the call can be repeated. It can also be called again on a `Closed` run when a payout that was in flight at closing later fails, or a claim is reopened; with nothing left it panics |

### Claims
All claim methods share these steps:
1. Run is `Active`, not paused, `now <= claim_deadline_ms`.
2. Recompute `leaf_hash` from `(run_key, chain, address, amount, salt_hex)`.
3. Verify the Merkle proof against `merkle_root`.
4. Verify authorization (method-specific, below).
5. `claimed` must not contain the key; insert it; `claimed_amount += amount`.
6. Pay with **one receipt to the token holding two actions**: `storage_deposit({account_id: target, registration_only: true})` with 0.00125 NEAR, then `ft_transfer(target, amount)` with 1 yoctoNEAR. The contract always sends the `storage_deposit` instead of first asking whether the target is registered; a NEP-145 token refunds the deposit when the account already is. The two actions are atomic: if either fails, both revert and the deposit comes back. Then callback `on_payout(run_key, leaf_hash_hex, amount, payout_kind)`.
7. In `on_payout`: if the receipt failed, remove the claimed key and subtract the amount (the claim can be retried). Emit `claimed` or `claim_failed`.

> **Before any mainnet use:** confirm that native USDC on NEAR handles `storage_deposit` with `registration_only: true` the same way as the standard implementation (registers a new account for at most 0.00125 NEAR, refunds the full deposit for a registered one, and does not panic). This has only been exercised against the mock token.

| Method | Authorization |
|---|---|
| `claim_near(run_key, leaf, proof, payout)` | `chain == "near"` and `env::predecessor_account_id() == address`. Called directly or through a NEP-366 meta-transaction (predecessor is still the recipient) |
| `claim_evm(run_key, leaf, proof, payout, destination_asset, destination_address, expires_at_ms, signature_hex)` | `chain == "evm"`; `destination_asset` and `destination_address` are only placed into the `to:` line of the message (the contract cannot check what 1Click delivers); `signature_hex` is `0x` + 130 lowercase hex; rebuild the claim message ([07](07-wallet-verification-and-claims.md)); EIP-191 hash with `env::keccak256`; recover with `env::ecrecover`; derived address must equal `address`; `now <= expires_at_ms` |
| `claim_solana(...)` (stretch) | `chain == "solana"`; `env::ed25519_verify(signature, message, pubkey)`; pubkey decoded from `address` |

`payout`:
```rust
pub enum Payout {
    NearFt { receiver: AccountId },            // USDC on NEAR
    OneClick { deposit_address: AccountId },   // 1Click deposit address on NEAR
}
```
JSON: `{"kind":"near_ft","receiver":"…"}` or `{"kind":"oneclick","deposit_address":"…"}`.

There is no `quote_ref` field: the 1Click deposit address already identifies the quote, it is the signed `payout_target`, and it is visible in the token transfer. The backend keeps the quote details in its own database.

Both resolve to an `ft_transfer` to an account. The kind and target are part of the signed message, so a relayer can't redirect funds.

### Refunds
| Method | Caller | Behaviour |
|---|---|---|
| `reopen_claim(run_key, leaf_hash_hex, amount: U128)` | an approver | For a 1Click payout that was refunded to this contract. Removes the claimed key (it must be set) and subtracts `amount` (must be ≤ `claimed_amount`; the approver is trusted to pass the leaf's amount). Emits `claim_reopened`. The UI must show the 1Click status `REFUNDED` before allowing this |

1Click quotes set `refundTo` = this contract and `refundType` = `ORIGIN_CHAIN`, so refunded USDC lands back here.

### Views
`get_config()`, `get_run(run_key)`, `is_claimed(run_key, leaf_hash_hex) -> bool`, `get_runs_by_approver(account_id, from?, limit?)` (at most 50 per call). Run views return hashes as lowercase hex and amounts as decimal strings.

| `claim_reopened` | `run_key`, `leaf_hash`, `by` |
| `run_closed` | `run_key`, `reclaimed_amount` (the amount sent by this call) |
| `run_cancelled` | `run_key`, `by` |
| `reclaim_failed` | `run_key`, `amount` |

## Invariants (test all of them)

1. `claimed_amount + reclaimed_amount <= funded_amount <= total_amount`.
2. A leaf can be paid at most once unless reopened by an approver.
3. Funds of one run can never pay a claim of another run (amounts are tracked per run, and claims check `amount <= funded_amount - claimed_amount - reclaimed_amount`).
4. Only `token_id` can fund.
5. A claim's payout target is exactly the one authorized by the recipient.
6. After `Closed`, no more claims.

## Gas and deposits

- Attach 100 TGas to claims. The contract reserves 10 TGas for `storage_deposit`, 15 TGas for `ft_transfer` and 10 TGas for the callback. Measured in the sandbox against the mock token: a claim burns about 8–9 TGas in total.
- Token `storage_deposit`s (0.00125 NEAR per payout target) are prepaid by run creators (see "Storage charge"). As a second guard, claims and reclaims are refused when the contract's spare balance (balance minus storage lock) is below 0.00125 NEAR + a 0.1 NEAR reserve, so keep at least ~0.2 NEAR spare on the contract account.
- Rust toolchain: builds and runs in the sandbox with rustc 1.96 and `cargo-near` 0.23 (near-sdk 5.30 needs rustc ≥ 1.95), so no `rust-toolchain.toml` pin is needed.
